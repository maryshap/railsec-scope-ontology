# Patch: protection and payload facts were attached to Interfaces, not flows

## What was wrong

`ontology/core.ttl` and `ontology/railway.ttl` declare `rdfs:domain
rss-core:InformationFlow` / `rss-rail:RailwayInformationFlow` for
`carriesPayload` and all 7 protection-control properties
(`authenticationEnabled`, `encryptionEnabled`, `integrityProtectionEnabled`,
`safetyCodeEnabled`, `sequenceProtectionEnabled`,
`sourceDestinationIdentifierEnabled`, `timeoutMechanismEnabled`).

`scripts/migrate_legacy_security_facts.py` resolved each legacy flow
identifier (e.g. `"IF-CT-01"`) against the case's `rsso:stableIdentifier`
index and asserted every property directly on whatever it found. The
identifier `"IF-CT-01"` belongs to the **Interface**
(`case:interface-if-ct-01`), not to either of the two directional
**RailwayInformationFlow** individuals that actually traverse it
(`flow-if-ct-01-forward` / `-reverse`, each with its own stable identifier,
`"IF-CT-01-forward"` / `"IF-CT-01-reverse"`). All 616 protection facts and
all 5 `carriesPayload` links in `cases/etcs/security-facts.ttl` ended up on
Interface individuals.

## Why this mattered, concretely

`rules/evaluate-transmission-threat.rq` and
`rules/evaluate-critical-violation.rq` both join on
`?flow a rss-rail:RailwayInformationFlow`, then read the protection
properties `OPTIONAL`ly off `?flow`. An Interface individual is never typed
`RailwayInformationFlow`, so it can never bind as `?flow`. The properties
sitting on the interface were therefore invisible to these two rule stages
for every one of the 88 interfaces, for the whole case, not just for any
one scenario.

**This does not produce false positives.** Both rules use `BOUND(...)` to
gate on whether a mechanism is known before deciding satisfied/notSatisfied
(see e.g. `?mechanismKnown` in `evaluate-transmission-threat.rq`) — an
unbound property correctly falls through to `undetermined`, not to a
fabricated "exposed" result. The practical effect is that the
transmission-threat stage has been returning `undetermined` for the
repetition/deletion/insertion/resequencing/corruption/masquerade threat
types across the real ETCS case, even though real protection-control data
exists and was correctly transferred from the legacy model — it just never
reached the node the rules read from. The transmission-*category* stage
(`transmission-environment.ttl`) is unaffected: those facts were already
attached to flows correctly, which is the working pattern this patch brings
the other file in line with.

## What changed

**`scripts/migrate_legacy_security_facts.py`** — for each matched legacy
flow, the script now looks up every `RailwayInformationFlow` that
`rss-core:traverses` the matched Interface and asserts each of the 7
protection properties (both the direct triple and its reified `Assumption`)
on every one of those flows, instead of on the Interface. This mirrors the
fan-out pattern `derive_transmission_environment.py` already uses for the
same reason (CR-B-022).

`carriesPayload` is **not** fanned out the same way. Payload content is
directional; protection controls are not. The script now leaves the 5
safety-related payload links unattached rather than guessing a direction —
see `cases/etcs/PAYLOAD_DIRECTION_TODO.md`.

**`cases/etcs/security-facts.ttl`** — regenerated by applying the same
transform directly to the committed file (the original legacy source
`.ttl` that the script takes as input is not in this repository, only its
already-migrated output was available to work from). Verified: 0 protection
properties remain on any Interface; all 1036 resulting protection triples
(616 → 1036 because interfaces with 2 flows now carry the fact on both) sit
on a `RailwayInformationFlow`; the file still parses as valid Turtle and
combines with `abox.ttl` + `classification-provenance.ttl` +
`transmission-environment.ttl` without error (16,202 triples total). The 5
mis-attached `carriesPayload` triples were removed, not reattached — they
are now genuinely absent rather than silently wrong, which is the correct
epistemic state until direction is sourced.

## What this does not fix

- Fail-safe/SIL will still not fire for this case — that's the separate,
  already-known `failSafeDependsOn` architecture gap.
- Critical-violation elevation for these 5 payloads will still be
  `undetermined` until `PAYLOAD_DIRECTION_TODO.md` is resolved — not
  because of this bug, but because direction genuinely isn't known yet.
- This has not been run through the full orchestrator (reasoner + rule
  fixed-point) here — that step didn't complete inside this session's time
  limit on the full graph, same limitation as before. The fix is verified
  at the data level (attachment, typing, parse, combination); the resulting
  evaluation counts need a real run on your machine/CI.
